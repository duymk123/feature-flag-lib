Feature Flag Library · Giải thích luồng hiện tại

5.000 feature flag được evaluate như thế nào?

Tài liệu trực quan về đường đi từ DB → cache RAM → đánh giá theo request → map kết quả trả về. Nội dung phản ánh source hiện tại của feature-flag-lib.

Kết luận quan trọng trước tiên

Hiện tại evaluateAll() dùng thread pool, mỗi task xử lý một flag. Số task đang chạy/chờ được giới hạn; task xong thì kết quả được thu về và submit flag tiếp theo. Request vẫn đợi đủ kết quả để trả map đầy đủ.

1. Cấu hình được đưa vào RAM lúc nào?

Khi ứng dụng khởi động, thư viện đọc cấu hình một lần để request không phải truy vấn DB cho từng flag.

1

Ứng dụng khởi động

Spring tạo FeatureFlagConfigServiceImpl, sau đó gọi hook initCache().

2

Đọc DB local

refreshCache() gọi featureFlagConfigRepo.findAll().

3

Nhóm theo tên

Tạo flagCache: tên flag → danh sách config của flag.

4

Lập chỉ mục ID

Tạo idCache để tra parent theo parentId.

5

Parse strategy

JSON strategy được chuyển thành object parsedStrategies để dùng lại khi evaluate.

flagCache

Ví dụ: FLAG_CHECKOUT → [config1, config2]. Nếu nhiều dòng DB cùng flag name, chúng nằm trong cùng danh sách.

idCache

Ví dụ: config-id → FeatureFlagConfig. Dùng để tìm cờ cha nhanh trong bộ nhớ.

5.000 dòng DB không nhất thiết là 5.000 flag. Số vòng lặp chính của evaluateAll() là số tên khác nhau trong flagCache.

2. Một lần login gọi evaluateAll()

1

Chụp context

captureContext() lấy username, authorities/roles và IP của request.

2

Lấy cache RAM

Dùng flagCache; nếu cache rỗng thì thử refreshCache().

3

Tạo map kết quả

Tạo HashMap có sức chứa ban đầu theo số flag trong cache.

4

Submit có giới hạn

CompletionService gửi từng flag; mỗi task dùng anyMatch để kiểm tra config của flag đó.

5

Trả map đầy đủ

Chỉ sau khi vòng lặp kết thúc, map flagName → Boolean mới được trả cho tầng gọi.

Submit tối đa 24 task→một flag hoàn tất→thu kết quả→submit flag tiếp theo 
EvaluationContext context = captureContext(); // chụp ThreadLocal trước khi dùng worker
Map<String, List<FeatureFlagConfig>> snapshot = new HashMap<>(flagCache);
CompletionService<FlagResult> completed = new ExecutorCompletionService<>(executor);
Map<Future<FlagResult>, String> pending = new HashMap<>();

// Chỉ submit đến max-pending-tasks.
submitUntilWindowFull(snapshot, context, completed, pending);

while (!pending.isEmpty()) {
    Future<FlagResult> finished = completed.take(); // request thread chờ kết quả
    FlagResult flagResult = finished.get();
    result.put(flagResult.name(), flagResult.enabled());
    submitNextFlag(); // worker đã xong task và được pool tái sử dụng
}
return result; // map đầy đủ mới trả cho login

Đây là giả mã giải thích cơ chế. Source bắt lỗi riêng theo flag; CompletionService.take() làm request thread chờ, worker không bị giữ để chờ task khác.

3. Bên trong evaluateConfig()

Mỗi config đi qua các điều kiện theo thứ tự. Điều kiện sai có thể kết thúc sớm, không cần chạy các bước sau.

  1. Kiểm tra công tắc: enabled không phải true → config false.
  2. Kiểm tra cha: có parentId thì isParentActive() tra trong idCache và đánh giá cha đệ quy. Cha tắt, không tồn tại hoặc có vòng lặp → config false.
  3. Không có strategy: config đã bật và không bị cha chặn → true.
  4. Có strategy: evaluateSingleStrategy() tìm handler trong strategyMap, rồi gọi strategy.evaluate(params, context).
  5. Kết hợp kết quả: logic AND cần mọi strategy true; mặc định/ OR chỉ cần một strategy true.

Nhiều config cùng tên

configs.stream().anyMatch(...): chỉ cần một config true thì kết quả của tên flag đó true. anyMatch dừng ngay khi tìm thấy config true.

Lỗi khi đánh giá

Lỗi trong config được bắt và coi là false. Ở cấp flag cũng có catch để tiếp tục vòng lặp với các flag còn lại.

4. Áp vào trường hợp 5.000 flag

Trong một request

  • Chụp context một lần.
  • Duyệt tối đa khoảng 5.000 tên flag nếu có 5.000 tên khác nhau.
  • Đánh giá rules/strategies cần thiết, có thể dừng sớm nhờ AND/OR.
  • Ghi tối đa 5.000 kết quả vào map.
  • Trả response sau khi hoàn tất lượt đánh giá.

Chi phí phụ thuộc vào

  • Số tên flag khác nhau, không chỉ số dòng DB.
  • Số config và strategies trên mỗi tên.
  • Số quan hệ cha–con cần lần theo.
  • Số strategy phải kiểm tra trước khi AND/OR có thể dừng.
Đừng nhầm map kết quả với cache config. Config/rules được giữ trong RAM để đọc nhanh. Map Boolean được tính theo context của lần gọi và trả về; các strategy vẫn được đánh giá lại khi có lần gọi evaluateAll() tiếp theo.

Mỗi lần gọi vẫn thực hiện 5.000 lượt đánh giá nếu có 5.000 tên flag, nhưng chỉ giữ tối đa 24 future đang chạy/chờ cho request đó. Pool và queue được cấu hình riêng trong feature-flag.executor.*.

Các hàm chính cần nhớ

HàmVai trò ngắn gọn
initCache()Hook sau khởi tạo service; gọi nạp dữ liệu vào cache.
refreshCache()Đọc DB, dựng map theo flag name và ID, parse trước strategies.
evaluateAll()Chụp context, submit từng flag có giới hạn, thu kết quả hoàn tất và trả map Boolean sau khi đủ.
captureContext()Thu thập username, authorities và IP của request hiện tại.
evaluateConfig()Kiểm tra enabled, parent, strategy và AND/OR cho một config.
isParentActive()Tra và đánh giá cờ cha; ngăn vòng lặp parent.
evaluateSingleStrategy()Chọn implementation strategy theo ID và gọi đánh giá.
parseStrategies()Chuyển JSON strategies thành danh sách object; thường đã được gọi khi refresh cache.
